01

Types & the Book

Build the data model and the book itself. No matching yet — just place and cancel.
cargo init structs enums BTreeMap HashMap

Recommended Data Structure

You said you don't want to think about this — so here's the answer. Don't second-guess it for now.

struct Order { id, side, price, qty, ts }

struct Book {
    bids: BTreeMap<Price, VecDeque<Order>>,
    asks: BTreeMap<Price, VecDeque<Order>>,
    by_id: HashMap<OrderId, (Side, Price)>,
}
Why this works: BTreeMap gives you O(log n) best-price lookup on either side. The VecDeque inside each price level enforces time-priority via push_back / pop_front. The auxiliary HashMap lets you cancel in O(log n) without scanning the whole book.
Don't use f64 for prices. Use integer ticks (e.g. cents as u64). Floating-point comparison will haunt you. For bids, iterate the BTreeMap in reverse to get best-first.

Tasks

  • cargo new --bin orderbook and set up modules: order, book, engine.
  • Define Side, OrderType (limit/market), Order, OrderId, Price, Qty as newtypes or aliases.
  • Build Book::new(), Book::add(order), Book::cancel(id). no matching yet — adding a buy at price 200 with asks resting at 100 is fine; just insert it.
  • Add Book::best_bid() / best_ask() / top_of_book().
  • Implement Display for the book so you can println! it during dev.
  • Unit tests: insert, cancel, cancel-missing, multiple price levels, FIFO order at a price.

Done when

cargo test passes.
You can drive the book from a test harness and print a sensible ladder.
best_bid < best_ask is always true after any operation.
02

The Matching Engine

Crossing orders match. Partial fills work. Trades are emitted as events.
price-time priority partial fills market orders iterators

The Algorithm in Words

For an incoming buy at limit price P:

  1. Look at the best ask. If it doesn't exist or its price > P, stop matching.
  2. Otherwise pop the front order at that price level. Fill min(its qty, remaining incoming).
  3. Emit a Trade. Decrement quantities. If the resting order is fully filled, drop it; otherwise push it back to the front.
  4. If the price level is empty, remove it from the book. Loop.
  5. When the incoming order is exhausted, stop. Otherwise rest the remainder on the bid side.

Sell is symmetric — swap "best ask" for "best bid" and flip the comparison.

Market orders are limit orders with effectively infinite (or zero) price. Same algorithm, just no resting step at the end.

Tasks

  • Refactor Book::add into a higher-level Engine::submit(order) -> SubmitResult.
  • SubmitResult = list of Trades + optional rested-order info.
  • Implement the match loop above. Watch out for borrow-checker pain when you mutate the same BTreeMap entry you're iterating. hint: take ownership of the front order with pop_front(), mutate, then conditionally push back.
  • Add OrderType::Market support.
  • Tests: empty book no-cross, exact match, partial-fill incoming, partial-fill resting, market eats multiple levels, market on empty book.
  • (Optional) IOC and FOK time-in-force flags.

Rust Concepts Used Here

BTreeMap::iter_mut first_entry / last_entry Vec<Trade> return match patterns borrow scoping mem::take
The borrow checker is going to push back here. When you remove an empty price level while iterating, you'll hit "cannot borrow as mutable more than once." Resolve it by structuring the loop with explicit peek-then-pop steps, not iter_mut walks.

Done when

Replay a fuzzy sequence of orders and the book/trade output is deterministic.
No order is ever lost (sum of resting + filled = sum of submitted).
03

Async Wrapper — the Actor Pattern

Wrap the engine in a tokio task. Talk to it via channels. Now you've crossed into async Rust.
tokio mpsc oneshot broadcast actor pattern

The Actor Pattern (read this first)

Instead of wrapping the book in Arc<Mutex<Book>>, give it to one tokio task and talk to that task with messages. The task is the sole owner. No locks, no contention, no Send/Sync drama for the book itself.

The Channel Cheat-sheet

mpsc — many-to-one commands oneshot — one-time reply broadcast — fan-out fills watch — latest top-of-book
The command enum carries its own reply channel: 
enum Cmd {
    Submit { order, reply: oneshot::Sender<SubmitResult> },
    Cancel { id,    reply: oneshot::Sender<bool> },
}

Tasks

  • Add tokio = { version = "1", features = ["full"] } to Cargo.toml.
  • Define Cmd enum with submit/cancel variants, each carrying a oneshot::Sender.
  • Write fn run_engine(mut rx: mpsc::Receiver<Cmd>, trade_tx: broadcast::Sender<Trade>). It owns the Engine and loops on rx.recv().await.
  • Wrap the API in an EngineHandle { cmd_tx, trade_tx } with friendly async fn submit(&self, o) -> SubmitResult methods. inside submit: create the oneshot pair, send the Cmd, await the receiver.
  • Write an integration test that spawns the engine task, sends 100 orders concurrently from tokio::join!'d clients, and verifies invariants.

Rust Concepts Used Here

#[tokio::main] tokio::spawn async fn / .await Send + 'static channels: mpsc/oneshot/broadcast Arc<EngineHandle> tokio::join!
Mental model: the engine task is a state machine driven by messages. It runs forever, processing one command at a time. Concurrency happens between clients, never inside the engine.

Done when

Multiple async clients hammer handle.submit().await concurrently and you get correct results.
A subscriber to the broadcast channel sees every Trade in order.
04

The TCP Server

External clients connect over the network, send orders, and receive fills in real time.
TcpListener BufReader::lines tokio::select! spawn-per-conn

The Per-Connection Task

This is where tokio::select! first earns its keep. Each connection task multiplexes two async sources at once:

  • Incoming command lines from the client socket.
  • Incoming fills from the broadcast channel.

Whichever fires first, handle it, then loop.

Cancellation safety matters in select!. read_line on a BufReader is cancel-safe. broadcast::Receiver::recv is cancel-safe. Most things on tokio's I/O traits are. If you write your own future, double-check the docs.

Wire protocol — keep it dumb

submit BUY  101 30
submit SELL 102 10
cancel 17

Line-delimited, space-separated. Don't reach for serde yet. Don't design a binary protocol yet. You're learning async, not codec design.

Tasks

  • Bind TcpListener in main. Accept loop: loop { let (sock, _) = listener.accept().await?; tokio::spawn(handle_conn(sock, engine.clone())); }.
  • In handle_conn: split the socket into read/write halves, wrap the read half in BufReader, get a fresh broadcast::Receiver from the engine handle.
  • Loop with select! over: (a) next line from client, (b) next trade from broadcast.
  • Parse the line, call engine.submit/cancel, write the response back to the client.
  • On a trade event, only forward it to this client if they were a party to the trade. tag orders with a client-id when submitting, so the engine can include it on each trade.
  • Handle connection close cleanly. read_line returning Ok(0) = EOF.
  • (Optional) tokio::signal::ctrl_c handler for graceful shutdown.

Rust Concepts Used Here

tokio::net::TcpListener AsyncReadExt / AsyncWriteExt BufReader::lines split / into_split tokio::select! cancellation safety graceful shutdown

Done when

nc localhost 7878 works as an interactive client.
Two terminals can both submit orders and see their fills.
Killing one client doesn't disturb the others or the engine.
05

Multi-symbol & Real Concurrency

One book per symbol. Each book runs in its own task — they match in parallel on multi-core.
router task parallel symbols backpressure tracing

Why the Router

Phase 3 had one engine. To scale, you need one engine per symbol: AAPL trades don't interact with BTC trades, so they can match in parallel. The router owns a HashMap<Symbol, mpsc::Sender<Cmd>> and routes each command to the right per-symbol task.

You can skip the router task itself by making the handle hold the HashMap directly — every connection task just looks up the right sender. Trade-off: less indirection, but you need Arc<HashMap> or DashMap if you add symbols at runtime.

Backpressure

Switch every channel to mpsc::channel(N) (bounded), not unbounded. A slow engine will eventually fill its inbox; send().await blocks the offending client until the engine catches up. That's the feature.

Never use try_send and silently drop. An exchange that drops orders is worse than one that's slow.

Tasks

  • Add a symbol field to Order. Update the wire protocol: submit AAPL BUY 101 30.
  • Refactor EngineHandle to either hold an Arc<HashMap<Symbol, mpsc::Sender<Cmd>>> directly, or talk to a router task.
  • Spawn one engine task per symbol at startup. Make the list configurable.
  • Switch all mpsc::unbounded_channel to bounded. Pick a capacity (e.g. 1024) and document why.
  • Add the tracing crate. Instrument submit, match_loop, and connection lifecycle. Use tracing_subscriber::fmt.
  • Write a synthetic load client: spawn 500 tokio tasks that each submit 1000 random orders. Measure throughput and p99 latency.
  • (Optional) Per-symbol top-of-book published on a watch channel.

Rust Concepts Used Here

bounded mpsc · backpressure Arc<HashMap> tokio::watch tracing / spans Instant / Duration multi-threaded runtime
By default #[tokio::main] uses the multi-threaded runtime, so per-symbol tasks really do run on different cores. You don't need to configure anything. Verify with top -H while load-testing.

Done when

Load test sustains thousands of orders/sec across multiple symbols.
A slow consumer on one symbol can't stall traffic on other symbols.
tracing logs show interleaved activity across engine tasks.
06

Durability & Recovery stretch

Survive a restart. Replay the world from disk. Optional but extremely educational.
tokio::fs spawn_blocking serde / bincode WAL + snapshots

The Idea

Before the engine task processes an accepted command, it appends a serialized record to a write-ahead log. On startup, the engine reads the log from disk and replays it before opening for new traffic. Periodically, write a snapshot of the book and truncate the log.

Tasks

  • Make every command and trade serializable via serde. Use bincode for compactness or JSONL for debuggability.
  • Open an append-only file. Inside the engine task: append the bytes, fsync (or batch fsyncs), then process the command.
  • Write a replay function that runs at startup and returns a rebuilt Engine.
  • Add a snapshot job: every N seconds, serialize the book state, rename-atomic-swap, then truncate the log.
  • Test: kill the process mid-load. Restart. Verify the book matches what should have been there.

Why It's Worth Doing

This phase teaches the messiest, most realistic part of building real systems in async Rust: when to use tokio::fs vs std::fs inside spawn_blocking, how to keep latency low when writes hit disk, and how to think about atomicity boundaries.

serde::{Serialize, Deserialize} bincode tokio::fs::OpenOptions spawn_blocking atomic rename BufWriter flush semantics

Done when

kill -9 the process mid-load. Restart. No order in the WAL is lost; no trade is duplicated.

Pitfalls You'll Hit (and How to Climb Out)

"future cannot be sent between threads safely"

You're holding a non-Send type across an .await. Common culprit: std::sync::MutexGuard, or a Rc. Either drop it before the await or use tokio::sync::Mutex.

Borrow checker fights inside the match loop

You can't mutate a BTreeMap entry while still holding an iterator over the map. Pop the front order out, mutate locally, decide what to push back. Don't try to be clever.

Channel fills up and everything stalls

That's backpressure working as intended. Increase capacity if it's a sustained issue; profile the engine task if it can't keep up. Don't switch to unbounded unless you can prove the producer is rate-limited.

Lost trades after a panic

A panic in a tokio task only kills that task — other tasks keep running with stale handles. Add JoinSet or supervise with tokio::select! on a watcher channel. Log panics explicitly.

"my select! arm cancelled mid-write"

Not all futures are cancellation-safe. Anything that writes to a socket or advances a stateful parser typically is not. Read the tokio docs for the specific method before using it in a select!.

It compiles but does the wrong thing

Write property tests: random sequences of orders → invariants must hold (no negative qty, best_bid < best_ask, trades balance). The borrow checker won't catch logic bugs.
